Index after waiting out a contended find-api cache lock

When another winapp process held the cache lock, the waiter polled for it,
took it, immediately released it inside the loop's `using`, and then returned
without indexing anything. The query went on to answer from a cache that was
never asked to include this caller's project.

The cache directory is shared by every project, so the process holding the lock
is very likely indexing a different project -- falling through was only correct
in the case where both processes happened to want the same one.

The wait now retains the lock it acquires and runs the index pass under it.
Giving up and querying whatever is on disk is kept for the case the lock is
still held after the full wait, since the other process may well have indexed
what this query needs.

This also removes a second, quieter cost: the old loop always slept the full
30 seconds even once the lock was free, because `break` only exited the retry,
after which it returned regardless. The new loop stops as soon as it has the
lock -- the regression test runs in ~3.8s against ~30.5s before.

Lock acquisition is now the only thing guarded by the IOException handler
(TryAcquireIndexLock), preserving the existing property that a genuine I/O
failure inside Refresh is not misreported as lock contention.

Verified the test fails without the fix: the SDK package source is never asked
for packages (0 calls, expected 1), and the run takes 30s.
